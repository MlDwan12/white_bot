# План: бот для рассылок постов и конкурсов в VK и MAX

Этот документ — единый источник правды по архитектуре, доменной модели, бизнес-флоу и порядку реализации. Обновляется по ходу разработки; ориентируемся на него в каждой сессии, а не переспрашиваем решённое заново.

## Контекст

Нужен бот, управляющий рассылкой постов и проведением конкурсов сразу в группах/чатах/каналах VK и MAX. Один владелец, много целевых групп — не мультитенантная SaaS-система. С августа 2025 MAX разрешает публикацию боевых ботов только через верифицированное юрлицо/ИП — токен уже есть, работаем с ним.

Репозиторий `anthropics/skills` (упомянутый изначально) — набор скиллов для самого Claude (документы, тестирование веб-приложений, генерация MCP-серверов), не библиотека для этого бэкенда. Вместо этого в разработке используются собственные скиллы Claude Code: `code-review` перед каждым коммитом, `security-review` перед тем, как в коде появляется реальная работа с токенами/логином, `run` — для ручной проверки веб-панели.

Процесс работы: на каждый шаг — обсуждение → список npm-пакетов (ставит пользователь сам) → реализация → команда коммита (тоже выполняет пользователь).

## Технологический стек

- **Backend**: NestJS + TypeScript.
- **БД**: PostgreSQL + Prisma ORM — типобезопасность результата запроса (тип отражает реально запрошенные `include`/`select`, в отличие от TypeORM) и декларативные миграции (`prisma migrate dev` на основе `schema.prisma`, без риска `synchronize: true`).
- **Очередь/расписание**: BullMQ + Redis — отложенная публикация, ретраи, отмена рассылки в процессе, авто-удаление постов, повторяющиеся посты. Обязательна уже в MVP — ориентир 20–200 целевых групп/чатов суммарно VK+MAX.
- **VK-интеграция**: `vk-io`.
- **MAX-интеграция**: официальный `@maxhub/max-bot-api` (TS SDK), `platform-api.max.ru`, токен в заголовке Authorization. Два типа целей: групповые чаты (до 1000 участников) и каналы (безлимитная аудитория) — обе поддерживаются под одной сущностью `Group`.
- **Приём апдейтов VK/MAX**: long polling (`bots.longpoll` / MAX `getUpdates`), не webhook — не требует публичного входящего соединения.
- **Админ-панель**: server-rendered прямо в NestJS, шаблонизатор **EJS** (HTML-разметку темы можно вставлять почти как есть, минимум трения по сравнению с Pug/Handlebars), вёрстка — тема **[Tabler](https://tabler.io)** (Bootstrap 5, MIT, готовые компоненты под таблицы статусов/карточки/бейджи).
- **Второй админ-интерфейс**: сам MAX-бот — полноценный интерфейс от `AdminUser` с привязанным `maxUserId`, включая создание поста/конкурса через пошаговый диалог (не только быстрые действия), поверх тех же сервисов, что и веб-панель. Требует stateful-диалога (`BotConversationSession` — шаг + черновик + `expiresAt` для авто-сброса брошенного диалога), выбор целей через чат — по тегам (не по отдельным группам при их большом числе — 200 кнопок-тумблеров технически влезает в лимит MAX, но нечитаемо), вложения — приём файлов прямо в переписке через `uploadAttachment`. У `maxUserId` может быть только **одна активная сессия одновременно** — попытка начать новый диалог (`/newpost` и т.п.) при незавершённом старом предлагает «закончить/отменить предыдущий диалог» вместо тихой перезаписи черновика. Создание/редактирование `AdminUser` через чат не поддерживается в принципе (см. «Защитный guard» ниже) — вложения/пароли туда не относятся. Точный сценарий диалога (порядок вопросов, `/cancel`, тайминги) прорабатывается отдельно на Шаге 5/6.
- **Хранение загруженных медиа** (фото/документы) до платформенной отправки — локальная папка на сервере под отдельным Docker volume (как Postgres/Redis), без объектного хранилища (S3) — избыточно при нашем масштабе и одном сервере.
- **Валидация**: `@nestjs/config` + Joi для env; `class-validator`/`class-transformer` для DTO.
- **Дев-инфраструктура**: `docker-compose.yml` (Postgres 16, Redis 7).

## Безопасность и эксплуатация

- **Шифрование токенов групп** — AES-256-GCM на уровне приложения, мастер-ключ в `.env` сервера (не в БД). Решено делать сразу, не откладывать. В панели токен не показывается полностью после сохранения — маска + кнопка «заменить». HTTP-клиент к VK и логирование Nest не должны писать полный URL (там `access_token` как query-параметр) в логи/трекинг ошибок.
- **Роли** (`AdminUser.role`): `developer` — полный доступ; `admin` — базово посты и конкурсы, группы видит только для выбора целей. Базовый набор по роли developer может точечно расширять на конкретного admin'а через `extraPermissions` (см. доменную модель `AdminUser` — полная матрица атомарных прав там). `AdminUser.maxUserId` (nullable) связывает веб-логин и MAX-команды в один `actorId` для аудита.
- **Bootstrap первого админа** — сид-скриптом на сервере (`yarn seed:admin`), не через публичную регистрацию.
- **Хостинг** — рекомендация: российский VPS (Timeweb Cloud / Selectel), 2 vCPU/4GB RAM, тот же docker-compose + prod-override (без публикации портов Postgres/Redis наружу), домен + TLS через Let's Encrypt/Caddy. Причина рекомендации РФ: участники конкурсов — персональные данные, вопрос локализации по 152-ФЗ — на стороне пользователя/юриста, не откладывать. Конкретный провайдер ещё не выбран.
- **Бэкапы** — мастер-ключ шифрования хранить отдельно от дампа БД.
- **Часовой пояс планирования** — фиксированно `Europe/Moscow` для всех админов и всего расписания (постов, recurring, авто-удаления) — без пользовательской настройки часового пояса на аккаунт.
- **Хранение данных участников конкурса** — бессрочно, автоматической очистки/TTL нет; ручная чистка при необходимости остаётся на усмотрение владельца (в т.ч. с учётом 152-ФЗ, если/когда это станет актуальным).
- **Деплой** — запуском Docker-образа на сервере (конкретный процесс — вручную/CI — уточняется позже, не блокирует разработку сейчас).
- **Алерты по группам** — статус в панели (`token_invalid`/`bot_removed` различаются) + сообщение в MAX-чат с ботом; уведомляем только при устойчивом переходе в нерабочее состояние (после исчерпания ретраев), не на каждую единичную неудачу.
- **Уведомление о завершении рассылки** — симметрично алертам об ошибках: по завершении кампании на все группы в MAX-чат с ботом уходит сводка («рассылка «Х»: 45/50 успешно, 5 ошибок»), а не только сигналы о проблемах.
- **Валидация лимитов контента** — длина текста и количество/размер вложений проверяются на известных ограничениях площадки в панели до отправки, чтобы ошибка была видна сразу, а не после провала `wall.post`/`sendMessage` на части групп.
- **Аутентификация панели (Шаг 9, решение зафиксировано заранее)**: access-токен (JWT, короткий TTL, например 15 мин) и refresh-токен (длинный TTL) — оба только в `httpOnly` + `secure` + `sameSite` куках, никогда в теле JSON-ответа и никогда в localStorage/sessionStorage (защита от кражи через XSS). Refresh-токены дополнительно трекаются в БД (таблица сессий: id, adminUserId, хэш токена, `expiresAt`, `revoked`) — чисто stateless JWT для refresh нельзя было бы отозвать раньше истечения срока, а нам это нужно: сброс пароля админом (`admins.manage`) и удаление/понижение админа должны отзывать его текущие сессии, а не просто менять пароль вхолостую. Именно из-за кук — обязателен CSRF (double-submit или аналог), проверить через `security-review` на этом шаге.
- **Конкурентное редактирование** — раз ролей и живых людей несколько, `Post`/`Contest` получают проверку по `updatedAt` при сохранении (и из панели, и из MAX-диалога — единая точка в сервисном слое, а не только в UI): если запись изменилась с момента открытия формы, сохранение отклоняется с «кто-то уже изменил, обновите данные» вместо тихой перезаписи.

## Доменная модель

### Group
- `id`, `platform` (`vk`|`max`), `kind` (VK: `community`; MAX: `chat`|`channel`), `externalId`, `title`, `accessTokenEncrypted`, `tags: string[]`, `status` (`pending_confirmation`|`active`|`token_invalid`|`bot_removed`|`removed`), `createdAt`.
- `pending_confirmation` — только для свежеобнаруженной MAX-группы до подтверждения админом. `removed` — мягкое удаление (строка остаётся ради истории `PostDelivery`, никогда не хард-делит).
- Уникальность по (`platform`, `externalId`).
- **VK-токен**: сейчас — ручная вставка токена **сообщества** (не личный OAuth-токен пользователя — community-токен привязан к одной группе, меньше урон при утечке). Получение токена реализуется как отдельный заменяемый шаг («TokenProvider»), не размазано по коду — при будущем переходе к мультитенантности OAuth встраивается как ещё один провайдер, без рефакторинга модуля Groups. При подключении — вызов `groups.getById()` без `group_id` (community-токен сам резолвится в свою группу), показываем админу название для подтверждения, что вставлен верный токен. Фиксируем конкретную версию VK API во всех вызовах, не полагаемся на дефолтную.
- **MAX-онбординг**: только через событие «бот добавлен в чат/канал» → черновик группы с названием → админ подтверждает и тегирует (или отклоняет — кнопка «отклонить» для случайных/нецелевых добавлений). Ручной ввод `chatId` как fallback не делаем. Повторное добавление бота в ранее известный (например, `bot_removed`) чат — реактивирует существующую запись по уникальности (`platform`+`externalId`), без повторного подтверждения и без дубликата.
- При создании — тестовая отправка «✅ Бот подключён» для проверки прав/токена сразу, а не при первой боевой рассылке.

### Post (кампания рассылки)
- `id`, `text` (общий текст по умолчанию), `vkTextOverride` (nullable), `maxTextOverride` (nullable) — при публикации на площадку сначала проверяется override для неё, иначе берётся общий `text`. Даёт и «один текст сразу», и «разный под каждую площадку» без двух отдельных сущностей поста.
- `attachments` (json) — общие для обеих площадок, per-platform override есть только для текста, не для вложений (сознательное упрощение MVP; расширяется аналогично тексту, если реально понадобится). `createdAt`.
- Расписание: `scheduledAt` (разово) **или** `recurrenceRule` (cron) — при recurrence на каждое срабатывание переиспользуется **тот же контент**, который админ может отредактировать в любой момент (правка меняет будущие срабатывания; уже отправленные прогоны трогаются только явным действием «редактировать опубликованный пост» для конкретного прогона). У recurring-**шаблона** (строка с заданным `recurrenceRule`, сама не проходящая через доставку) — отдельное булево поле `templatePaused`, не смешанное с `status` конкретных отправленных вхождений (это разные по смыслу жизненные циклы).
- Авто-удаление: `autoDeleteAt` (абсолютное) **и/или** `autoDeleteAfterMinutes` (относительное) — поддерживаются оба варианта.
- `status` (для конкретного поста/вхождения, не для recurring-шаблона): `draft → scheduled → sending → {sent | partially_failed | stopped}`. `stopped` — не тупик: после «отправить оставшимся» статус возвращается в `sending` и снова разрешается в `sent`/`partially_failed`/`stopped` по факту оставшихся доставок.
- `stopRequested: boolean` — воркер проверяет перед каждой следующей группой; необработанные помечаются `skipped_by_stop`.
- `clonedFromPostId` (nullable) — клон при добавлении новой группы к уже отправленной кампании.
- `recurringTemplateId` (nullable) — если пост порождён срабатыванием повторяющегося шаблона: каждое срабатывание создаёт отдельную дочернюю запись `Post` (снимок текста/вложений/целей шаблона на тот момент), которая живёт по обычному жизненному циклу (`sending`/`stop`/`edit`/`delete`) независимо от других вхождений. Правка/пауза/удаление самого шаблона влияют только на будущие вхождения. Это отдельное поле от `clonedFromPostId` — разный смысл связи.
- **Список целей замораживается в момент создания поста** (снапшот конкретных `Group.id`, не живой пересчёт по тегу) — новая группа, добавленная в тег после создания поста, в уже запланированную рассылку не попадает. Для **разовых** постов список целей неизменен после создания.
- **Для повторяющихся постов** (`recurrenceRule` задан) — список целей, как и контент, **можно редактировать** после создания: правка влияет только на будущие срабатывания, уже отправленные прогоны не трогает (симметрично с редактированием контента).

### PostDelivery
- `postId`, `groupId`, `status` (`pending`|`sending`|`sent`|`failed`|`skipped_by_stop`|`unknown`), `externalMessageId` (id поста VK / сообщения MAX — обязателен для последующего edit/delete), `error`, `sentAt`, `attemptsMade`.
- Перед вызовом API статус сохраняется как `sending` (коммит в БД до похода в сеть) — если воркер упал и доставка зависла в `sending` дольше таймаута, она переводится в `unknown` и не ретраится автоматически (риск задвоить пост в группе). Разрешение `unknown` — вручную, два действия на выбор админа: **«Отметить отправленным»** (если проверил в самой группе вручную, что пост есть — но без `externalMessageId`, то есть без возможности впоследствии его отредактировать/удалить через это же удобство) или **«Отправить заново»** (трактовать как неудачу, отправить через обычный retry/resume — на собственный риск задвоения, если на самом деле уже ушло).
- Автоматический ретрай — только для временных ошибок (сеть/rate-limit), 2-3 попытки с задержкой, после исчерпания — статус `failed`. Ошибки авторизации (401/403) не ретраятся автоматически — группа сразу помечается проблемной.
- «Отправить оставшимся» — довыполнение только `skipped_by_stop`/`failed` доставок без создания нового поста (использует актуальный контент поста на момент нажатия — то есть уже с учётом более ранних правок).
- **Редактирование поста** (в т.ч. пока ещё `sending`) — клик "Редактировать" во время активной рассылки сначала выставляет `stopRequested` (необработанные доставки уходят в `skipped_by_stop`), сохраняет новый контент, затем **автоматически** проталкивает его во все уже `sent`-доставки через `wall.edit`/`editMessage` — без отдельного подтверждения, это и есть смысл редактирования опубликованного. После этого «отправить оставшимся» уходит уже с новым контентом.
- **Удаление опубликованного** — админ выбирает конкретные группы для удаления (по умолчанию в UI отмечены все, но можно снять галочки и удалить точечно, например при жалобе на одну группу, не трогая остальные).

### Contest
- `id`, `postId` (nullable — конкурс может быть без анонс-поста), `title`, `status` (`draft`|`open`|`drawn`), `createdAt`.
- `draft → open` — явная кнопка **«Открыть приём участников»**, независимая от публикации анонс-поста (раз `postId` необязателен, открытие не может быть автоматическим следствием отправки поста).
- Без формального дедлайна участия — участники добавляются, пока статус `open`; момент закрытия набора определяется самим действием «провести розыгрыш» (переводит в `drawn`), не отдельным полем даты. Кнопка «Провести розыгрыш» недоступна повторно при `status=drawn` — только точечные правки отдельных мест.

### ContestParticipant
- `id`, `contestId`, `displayName`, `vkId` (nullable), `maxId` (nullable). Ввод — вставка списком, по одному на строку, формат «Имя + ссылка/ник»: например `Иван Иванов, vk.com/id123` или `Иван Иванов @max_nick`. Парсер распознаёт `vk.com/id<N>`/`vk.com/<screen_name>` → `vkId`, `@handle` → `maxId`, остальное — `displayName`. Строки без распознанной ссылки — просто `displayName`, без id (тогда авто-DM для такого участника недоступен, только ручное уведомление).
- Дедупликация/предупреждение при повторе одного и того же участника (по `vkId`/`maxId`, если есть, иначе по точному совпадению `displayName`) в списке.

### ContestPrize
- `id`, `contestId`, `place` (int), `label`, `winnerParticipantId` (nullable до розыгрыша), `isForced` (true = «подкрутка», победитель назначен вручную).
- **Один участник может занять не более одного призового места в рамках одного конкурса** — уже выигравший исключается из пула при розыгрыше оставшихся мест.
- Розыгрыш не-форсированных мест — криптостойкий рандом (`crypto.randomInt`), не `Math.random()`.

### ContestDrawLog
- `id`, `contestId`, `drawnAt`, `resultSnapshot` (json), `note`, `actorId`.
- Ручное изменение уже определённого победителя — старое/новое значение с timestamp отдельной записью, не молчаливая перезапись.
- **Автоуведомление победителя** личным сообщением (VK `messages.send` / MAX `sendMessage`) — если нет платформенного id или отправка не удалась (пользователь не писал боту, отключены сообщения от сообщества и т.п. — риск, который нужно проверить эмпирически на реальных токенах), победитель помечается «нужно уведомить вручную» вместо тихого отказа. Не полагаемся на автосообщение как единственный канал.

### AdminUser
- `id`, `email`, `passwordHash`, `role` (`developer`|`admin`), `maxUserId` (nullable) — если заполнено, тот же аккаунт отдаёт команды боту прямо из MAX-чата; веб-логин и MAX-команды — один `actorId` для аудита. MAX-бот применяет ту же матрицу прав, что и веб-панель — команда, требующая недостающих прав, отклоняется так же, как в UI.
- `extraPermissions: Permission[]` (json-массив, по умолчанию пусто) — **точечные права сверх базовых для роли**, которые `developer` может выдать конкретному `admin`-аккаунту, не меняя роль и не заводя третью роль ради одного человека. Только на расширение, не на урезание — `admin` не может иметь меньше прав, чем базовый набор роли.
- Эффективное право = `ROLE_DEFAULTS[role]` ∪ `extraPermissions`. У `developer` `extraPermissions` не имеет смысла — у роли и так все права.

### AdminSession
- `id`, `adminUserId`, `refreshTokenHash`, `expiresAt`, `revoked: boolean`, `createdAt` — server-side учёт refresh-токенов ради возможности их отзыва (сброс пароля, удаление/понижение админа — см. «Аутентификация панели» в разделе безопасности). Access/refresh токены сами по себе живут только в `httpOnly`-куках, не в теле ответа.

**Атомарные права (`Permission`) и базовый набор по ролям:**

| Право | `developer` (база) | `admin` (база) |
|---|---|---|
| `groups.manage` (жизненный цикл группы: создание/переименование/деактивация/реактивация) | ✅ | ❌ |
| `groups.tags.edit` | ✅ | ❌ *(можно выдать точечно через `extraPermissions`)* |
| `groups.tokens.manage` (ротация/просмотр маски) | ✅ | ❌ |
| `groups.pendingMax.review` (подтвердить/отклонить новую MAX-группу) | ✅ | ❌ |
| `groups.view` (список для выбора целей поста) | ✅ | ✅ |
| `posts.manage` (создать/редактировать/планировать/отправить/стоп/удалить/resume/recurring) | ✅ | ✅ |
| `contests.manage` (участники/призы/розыгрыш/результат) | ✅ | ✅ |
| `admins.manage` (создать/удалить/сменить роль/выдать `extraPermissions`/сбросить пароль другого админа) | ✅ | ❌ |
| `system.health` | ✅ | ❌ |
| `audit.viewAll` (лог всех админов, не только свой) | ✅ | ❌ *(можно выдать точечно)* |

Границы по умолчанию сознательно строгие — `groups.tags.edit`, `groups.pendingMax.review` и `audit.viewAll` разведены в отдельные атомарные права именно для того, чтобы их можно было выдать конкретному admin'у точечно, не открывая всё управление группами или полный аудит.

**Защитный guard**: нельзя удалить/деактивировать последний оставшийся аккаунт с ролью `developer` и нельзя понизить его роль до `admin`, если он единственный — иначе можно случайно заблокировать себе полный доступ без возможности восстановления через панель (только через сид-скрипт на сервере, как при bootstrap).

**Создание/редактирование `AdminUser` — только через веб-панель**, даже несмотря на то, что MAX-бот в остальном полноценный интерфейс: пароль, введённый прямо в чат, навсегда остаётся в истории переписки — это небезопасно по своей природе, не вопрос реализации. Бот может прислать ссылку на нужный экран панели, но не принимает пароль как текст диалога.

## Пайплайн рассылки — очередь и лимиты

- Rate-limit **per-group** (per-token), не единый глобальный лимитер: к разным VK-группам можно стучаться параллельно (у каждой свой токен), а несколько последовательных вызовов в одну группу (загрузка фото → `wall.post`) — придерживать (~3 запроса/сек ориентир для VK). Для MAX лимиты не задокументированы — подбираются эмпирически на реальном токене в Шаге 5.
- Порядок отправки по группам в рамках одной кампании — **неважен** (никакого приоритета/ручной сортировки в MVP), обычный мультиселект без drag-реордера.
- Провал джобы после исчерпания ретраев напрямую триггерит уже описанный механизм алертов (статус группы + сообщение в MAX-чат) — та же система, не отдельная.

## Розыгрыш конкурса — механика

- Одно действие «Провести розыгрыш» обрабатывает **все призовые места сразу**: форсированные (`isForced`) — просто назначаются, остальные — крипто-рандом из пула участников за вычетом уже занятых (форсированных и случайно выигравших) мест. Один `drawnAt` на весь розыгрыш. Точечные правки отдельных мест после — по-прежнему возможны (лог старое/новое), живого пошагового раскрытия по местам не делаем.
- Если участников меньше, чем оставшихся нефорсированных мест — явная ошибка «недостаточно участников», без падения/задвоения победителя.
- После перехода конкурса в `drawn` — добавление новых участников блокируется (поздно, розыгрыш уже прошёл), правка данных уже существующих участников (опечатки) остаётся доступной.

## Бизнес-флоу и подводные камни

**Публикация поста**: создание → выбор целей (снапшот) → сразу/по расписанию → BullMQ фан-аут по группам с интервалом (rate-limit) → живой прогресс по группам в панели → `stopRequested` останавливает необработанные → отдельное действие «удалить уже отправленное» (не автоматическое следствие стопа) → «отправить оставшимся» довыполняет пропущенное. Редактирование опубликованного — правит текст/вложения во всех `sent`-доставках через `wall.edit`/`editMessage`; смена картинки на VK требует повторной загрузки под upload-server каждой группы. Добавление новой группы к уже отправленной кампании — отдельный пост-клон, а не мутация истории.

**Повторяющиеся посты**: один и тот же (редактируемый) контент на расписании, статус `paused` отдельно от удаления.

**Конкурс**: список участников (дедуп) → призовые места (1..N, не более одного места на участника) → розыгрыш (форсированные места вручную, остальные — крипто-рандом среди оставшихся) → лог → авто-DM победителю с ручным fallback → отдельный пост-результат, публикуемый по подтверждению админа.

**Онбординг группы**: VK — токен сообщества, проверка через `groups.getById`; MAX — через событие «бот добавлен», подтверждение в панели. Тестовое сообщение сразу после подключения.

**Ошибки токена/доступа**: 401/403 → статус группы `token_invalid`/`bot_removed`, автоматические ретраи отключаются для этой группы, алерт в панель + MAX-чат при устойчивом отказе (не на каждую единичную неудачу).

**Bootstrap первого админа**: сид-скрипт на сервере, не публичная регистрация.

## Фазировка типов контента

1. **Фаза 1** (Шаги 4-5 ниже): текст + фото (в т.ч. несколько) + документы.
2. **Фаза 2** (отдельный подшаг после обкатки публикации/edit/delete/stop на простых вложениях): видео (асинхронная обработка на VK — `video.save` + опрос готовности перед прикреплением) и VK-опросы (платформенно-асимметрично: у MAX нет нативного аналога, только inline-кнопки — если понадобится и там, это отдельная реализация голосования).

## Порядок реализации

1. **Фундамент** (в процессе): поднять Docker, `docker-compose up -d`, `prisma generate`, проверить `GET /health` — коммит после проверки.
2. **Доменная схема**: все модели выше в `schema.prisma`, `prisma migrate dev --name init`.
3. **Модуль Groups**: CRUD, шифрование токена, тестовое сообщение при подключении, MAX-онбординг через событие.
4. **VK-интеграция**: `wall.post`/`wall.edit`/`wall.delete`, загрузка вложений (фаза 1: фото/документы).
5. **MAX-интеграция (базовая)**: `sendMessage`/`editMessage`/`deleteMessage`/`uploadAttachment`, приём апдейтов, распознавание прав по `AdminUser.maxUserId`.
6. **Пайплайн рассылки**: BullMQ — публикация, ретраи с учётом типа ошибки, `stopRequested`, «отправить оставшимся», авто-удаление (relative/absolute), recurring через cron-джобы.
7. **Модуль Contests**: участники (дедуп), призовые места (один участник — одно место), розыгрыш (forced + crypto-random), лог, авто-DM с fallback.
8. **Веб-панель**: группы (с ролевыми ограничениями для `admin`), создание/редактирование поста, список кампаний со статусами, управление конкурсом/розыгрышем.
9. **Аутентификация панели**: email/password, роли, `extraPermissions`, CSRF/cookie, оптимистичная блокировка по `updatedAt` — через `security-review`.
10. **MAX-бот как полноценный интерфейс**: `BotConversationSession`, пошаговый диалог создания поста/конкурса, быстрые действия кнопками — отдельная детальная проработка сценария диалога перед реализацией.
11. **Деплой**: production docker-compose (включая volume для медиа), домен+TLS, сид первого админа.
12. **Фаза 2 контента**: видео, VK-опросы — отдельным подшагом после стабилизации базового пайплайна.

## Проверка после каждого шага

- Jest-тесты на бизнес-логику (расчёт recurrence, выбор победителя с учётом forced-мест и лимита «одно место на участника», переходы статусов кампании).
- Ручная проверка `GET /health` и реальные вызовы к VK/MAX на тестовой группе/чате.
- **После завершения каждого этапа — жёсткое независимое ревью** (`code-review` на повышенном уровне) целенаправленно на баги, дыры безопасности и утечки данных/секретов, не только на качество кода. Перед работой с токенами и логином панели — дополнительно `security-review`. Это стандартный шаг процесса, не разовая мера.
